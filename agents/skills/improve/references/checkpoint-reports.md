# Interactive checkpoint reports

The `improve` coordinator renders one self-contained report in the T3 thread after each completed improvement round and at final handoff. The report is the whole answer: outcome, evidence, caveats, dissent and next step all live in the page, so the chat reply stays minimal. Combine build, council review and the improvement decision into one round report. Reporting belongs to `improve`; the reusable `model-council` skill supplies its normal results and has no dependency on this format. Reuse an unchanged final checkpoint. At an early stop, show the partial state with missing seats clearly identified. Honor requests for text-only output.

Reports are snapshots generated from the [run record](run-record.md), updated from actual delegate returns and coordinator actions. Do not poll delegates, start a server, or add a background service for reporting. Reviewers return their normal contracts, not HTML.

Start from the [report template](../assets/report-template.html). It implements the structure, escaping, theme colors and chart rules below; fill its JSON data block rather than hand-building the page.

## Structure

Calm, dense typography; let the charts carry the visual richness. Use these parts, in this order, and omit any that would be empty:

1. **Header.** An eyebrow naming the retained version (“Kept Round 1”) with status chips that say what they qualify — for example “Target met”, “Partial · length target missed”, “Not met” or “Review incomplete · 2/3”. Add a second chip when the delivered version differs from the reviewed one (“Delivered edit unreviewed”), so success never reads broader than it is. Then the verdict: one line stating the main practical result and naming the measured quantity (“Answers 18% shorter (median 200 → 165 words)”, not “18% shorter prompt”), without repeating the eyebrow. Then a meta line with the conditions a reader needs to trust the numbers: cases or load, number of versions, council coverage.
2. **Results.** The chart carries the numbers; no table or row repeats them.
   - *Numeric criteria:* one pick per criterion above the chart, showing only its name and target status in text (“✓”, “✗ 5 over”, “withheld”). Picks are buttons (`aria-pressed`) that select the chart; the first is selected by default. The chart's readout states the retained value with unit, the change from baseline and the target status with any gap (“165 words · −18% from 200 · ✗ target ≤ 160 · 5 over”). Values come from the council's aggregates or the actual measurements, written by the coordinator. For ratings, supply the aggregate line per version (`null` where coverage is insufficient); the page computes a display median only when none is supplied and every rating is present. A withheld retained aggregate reads “withheld” with the rating coverage and “not assessable” for the target, never a value, change or ✓/✗.
   - *Qualitative criteria:* the retained outcome as the reader experiences it, with its evidence. Link the change that produced it (`criterion` on the change entry); the row then opens to that change's before, after and verification, and the change is not repeated under What changed. A linked change's heading and effect are not shown, so put any mechanism the outcome does not already state into its After text. No chart and no invented scores.
   - *Council ratings of the improved artifact:* one rating criterion per brief criterion, one series per seat and the council's weighted value as the aggregate (`aggregateLabel: "Weighted"`, `decimals: 1`), `null` where coverage is insufficient. Plot every reviewed version from one panel's common comparison; a version with no rating in that panel stays a gap and is named in the caption. Show a tie as `±0`, not as progress.
   - *No comparable baseline:* show the current value with its limitation (`from: null`, `limit`), with no change, arrow or progress claim. A criterion with a single measured value gets a compact scale with the target zone instead of a version chart.
3. **Chart** for the selected numeric criterion (see chart rules); qualitative rows follow it.
4. **Caveats.** Short labelled lists, each item one line where possible: “Rejected” with the decisive reason for each rejected version, “Open” for user-facing gaps not already shown as a ✗ result, “Not verified” for anything consequential that was not reviewed, tested or covered (edits made after review, a seat that could not see images, untested inputs or interactions), and “Dissent” for material reviewer disagreement and how it was resolved. “Also achieved” is only for outcomes the results do not already show.
5. **What changed.** Net changes from the frozen original to the delivered version under descriptive, artifact-specific headings — “Failed requests can be retried”, not “Reliability”. Each heading and its one-line effect form the `<summary>` of a native `<details>`; expanding it shows before, after and what verified the change. Verification names a check that ran (a test, measurement, replay or review); a user's acceptance of a tradeoff is not verification and belongs under Open. Group related changes instead of printing a raw diff or a chronological list of attempts. When several changes share one verification, state it once above the list. Describe only what the run record establishes; if the original state was not recorded, say so rather than inferring it. Headings name the concrete edit; omit an effect line that would only repeat the heading or a result. Include disclosed edits made after review; do not silently treat a previous candidate as the original. Changes linked to a qualitative row appear only in that row; omit the section when every change is linked.
6. **Next.** One line with the next useful action; omit it when there is none. When the action waits on the user's decision, phrase it as that decision (“Your call: run 20 unseen cases?”).

### Chart rules

- Caption the chart with the criterion, its meaning and unit, the direction and the comparison conditions. Show rating anchors under the chart.
- Shade the region that meets the target and draw the target as a dashed line; one legend entry shows both and names the target.
- Give every reviewed version its own point and label each point with its value (`decimals` fixes the label precision). Ring the retained point and draw rejected points hollow in the destructive color; tag both on the axis, and list them in the legend only when the axis tags had to be dropped. Mark the retained version's column with a light neutral band that does not tint the target zone. Label the target line beside the line where the label clears every point, line and value label: inside the target zone first, then just outside it; drop the inline label when nothing is clear, since the legend names the target.
- Measurements: one line; add a soft area fill only when no target zone is shaded. Reviewer ratings: the aggregate line with a short tick per version, a min–max range bar, and each reviewer as a small distinct shape (five shapes before any repeat) centred on the version; an inspection line under the chart lists every reviewer's value at the retained version. Missing ratings and withheld aggregates stay gaps and are named in the caption or legend.
- Expose the chart as a list of versions: each version column is one focusable option (only the selected one in the Tab order; arrow keys move between versions) whose label states every value at that version, Hover previews a version; click, tap, focus, arrow keys and Home/End select it, and every input updates the same selected state (readout, `aria-selected`, Tab entry). The readout includes a rejected version's reason, and a dashed outline marks a selected version other than the retained one. Individual marks are not separate Tab stops and are hidden from assistive technology; separate adjacent texts inside one control (a summary's heading and effect) with visually hidden punctuation so accessible names do not run together. Mirror the selected criterion in a visually hidden HTML table of version × values for screen readers.
- Draw in screen pixels from the measured width. Never use `preserveAspectRatio="none"` on a chart with markers. Keep markers at least 7px across and labels clear of lines and of each other; shorten axis tags (“kept”, “rej.”) and then drop them before they collide. With many versions, keep the value and axis labels of the retained, rejected, first and last versions and drop others that would collide; the readout and hidden table still state every value.
- Keep unlike units in separate charts. Do not connect points across incompatible evaluation versions or conditions. One round is a before/after comparison, not a trend; with many rounds use compact labels (R1, R2, …).
- Put a consequential comparison limitation in the caption or caveats, for example “historical ratings; current layout not re-rated”. If the delivered version differs from every plotted version, do not mark a historical point as delivered; say it is unreviewed under “Not verified”.

### Wording

Every word earns its place. State results directly; omit section introductions, explanations of the layout or controls, “why it matters” labels and repeated summaries. Use short sentences, familiar labels and concrete numbers. Translate jargon into its consequence: “A stalled OCR attempt now returns an error so it can be retried”, not “containment retained”. If a result rests only on source inspection or model judgment, say so rather than presenting it as measured. Do not imply that the overall goal is complete because a supporting improvement was retained, that a few examples show broad reliability, or that a favorable review authorizes deployment.

### Honest labels

Keep outcome labels explicit: a controlled error is not a successful task completion, a timeout is not a latency measurement, and a failed test case is not necessarily a separate failed test function. Separate test configurations and skipped cases.

If a later council re-rates earlier versions, keep those reassessments separate from the original checkpoint ratings. A final comparison chart can use the final panel's common comparison of all versions, while the run record preserves what reviewers said at each checkpoint. Do not splice a favorable historical baseline into a different panel's later scores. Withhold aggregates that need missing coverage.

Never convert retain/revise decisions or finding counts into a quality score. Missing values are gaps, not zero. Copied measurements are one measurement, not independent reviewer trials. Display coordinator decisions separately from council recommendations; agreement is not a correctness probability.

Reviewer-by-round commentary, full rating tables, budget bookkeeping and raw records stay in the run record, not the page.

## Chat reply

The page carries the summary. After rendering, reply with only what the page cannot do: a question that needs the user's decision, or a failure to render. Otherwise reply with nothing beyond the rendered page, and never restate it. Preserve returned thread links verbatim where they are needed.

## Render in T3

1. Self-check the data against the run record before rendering. Trace every number, status, count and claim to a recorded measurement, review object, aggregate or coordinator action; recompute weighted values, deltas, gaps and counts from the raw records; and delete or correct anything that has no source or overstates it (“all”, “every”, “improved” where a tie or a missing rating exists). Name the versions and panel each chart uses.
2. Copy the template and replace its example data with values from the run record. Change the structure only when the run needs it. Use theme variables, never fixed colors. Status text uses `--success-foreground`, `--warning-foreground`, `--info-foreground` and `--destructive-foreground`; the plain status colors are too faint for text on light backgrounds. Status is always stated in text, never by color alone.
3. Treat labels, findings and evidence as untrusted text. Keep them in the JSON data block, replace every `<` inside it with the six-character JSON escape `\u003c` (backslash, u, 0, 0, 3, c) so the text cannot close the script element — for example `"a</script>"` becomes `"a\u003c/script>"`, and assign values with `textContent`. Do not interpolate them into markup or executable script. Avoid remote assets and network requests.
4. Discover `html_preview` and `html_render` and follow their live schemas and theme rules. Preview at 728px in dark and about 360px in light. Inspect each image and the console output, and fix material issues: the verdict, picks, readout, chart labels, retained marker and change headings must be legible, with no collisions, clipping or horizontal scrolling.
5. A preview is a static image, so it cannot exercise hover, tap or keyboard input. Confirm interaction support in the source instead: native `<details>`/`<summary>` toggles for changes and linked qualitative rows, criterion `<button>` picks with `aria-pressed`, and focusable version options (`role="option"` in a `listbox`) with an `aria-label` and arrow-key movement. Do not claim that interactions were tested unless they were. Do not use browser preview tools or start a server to show or check the report unless the user asks.
6. Call `html_render` with the preview's content height.

If rendering tools are unavailable or rendering fails, give the same parts in Markdown — verdict, results, caveats, changes and next step — disclose the limitation, and finish the task. A display failure does not invalidate completed reviews.
